## 二、这一波的设计取舍（值得留档）

1. **一句话生成怎么不越界**：云端只回答"做什么、找哪块文字、做完应看到什么"，
   **坐标由本机在用户框的那张页面截图上按文字找**（`engine/autofill.py`）。
   于是链子是"云端出意图 → 本地出坐标"，而不是让云端顺手把位置也定了。
2. **出口 ② 没授权时明确失败，不悄悄退回出口 ①**：用户要的是代码脚本，
   给他一个别的东西比不给他更糟（他会以为拿到了源码）。
3. **默认不覆盖别人的文件**：冲突策略默认"跳过"；覆盖要显式选择，且先备份 `.bak`；
   所有写入路径都先校验"是否在目标目录之内"。
4. **导出物不是自包含代码**（§8.2 ⚠️）——这句话写进了两种产物的文件头，
   因为用户最容易误解的就是这一点。

## 三、过程中发现并修掉的真问题

| # | 问题 | 怎么发现的 |
| --- | --- | --- |
| 1 | 生成的 skill 调 `_fill()` 却**没导入** → 产物一 import 就崩 | e2e 的"import + build_task + 真跑"（"能编译"≠"能跑"） |
| 2 | 引用完整性校验逻辑**写反了**（变成"有引用才报错"） | 单测；改成用 AST 找 `click("部件名")` 再核对注册表 |
| 3 | 中文脚本名被 ASCII 白名单清空 → 所有 skill 都叫 `script.py` | 单测；Python 3 的标识符本来就允许 Unicode |
| 4 | `page["bgr"]` 是 numpy 数组不能直接判真 → 真机上表现为"点了没反应" | 单测 |
| 5 | 手输目录**不触发扫描** → 用户敲完路径什么都看不到 | 界面自测 |
| 6 | "为什么没成"写进了 `notes`，但**界面根本没渲染 notes** | 界面自测（用户只看到"回到上一步"，不知道原因） |
| 7 | 我自己的脚手架：`run_script` 在主线程跑、Tk 不 pump → 点击效果永不发生；裸用默认 `RunConfig` → 定位不到时**热循环烧了 86s CPU** | 真机 e2e 卡住（同一个坑在 M3 的回放测试里记过一次，这次又犯了） |
| 8 | 同一个进程里先后从两个目录 import 同名模块 → 拿到上一份缓存 | 真机 e2e（"重新导出后没生效"那类困惑的来源） |

## 四、已知局限（不假装支持）

1. **文本匹配的固有歧义**：一句话生成的"用户名"，若页面上是**标签**而不是输入框，
   补齐会落在标签上，文字就进不了输入框。真实使用里用户把这一步的目标改一下即可；
   要自动解决需要识别"输入框"这一控件类型（UIA 能覆盖一部分，但不通用）。
2. **出口 ② 的产物质量依赖云端模型**：本表数字是能力证明，不是稳定性承诺。
3. **`smoke/diag/generate_e2e.py` 只验到"生成 + 补齐 + 真值对比"**：真跑那一步依赖
   实时桌面的页面定位（受窗口层级/遮挡影响），已通过一次但不作为日常复跑项。
4. **WIDGETS 用 base64 内嵌**（§8.7 定案）：单文件会随部件数变大；本次实测
   4 个部件的 screen.py 约 190KB。若将来显著变大，再按 §8.7 注里的"外链"思路另议。
5. **本轮的"真实 Agent 目录"仍是合成的**：用户未提供真实目录，已按 §8.6 约定造了
   一个含 `skills/`、`tools/`、自定义 `registry.py` 与已有工具实现的项目当靶子。
