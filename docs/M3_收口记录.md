## 二、录制→回放闭环（① 的最终验收）

`smoke/diag/e2e_replay.py` 做的是：造一个受控窗口 → 用合成真实输入把一段操作**录下来**
→ 清空现场 → 用执行器把录到的脚本**原样跑一遍**（human=None，无人值守）→ 核对窗口状态。

| 场景 | 录出的积木 | 回放 | 结果 |
| --- | --- | --- | --- |
| 点输入框 → 打字 → 停顿 → 点确定 | 点一下 / 输入文字「demo」 / 等一下 2.29 秒 / 点一下 | 7.1s，4 步全 ok | ✓ 按钮 1 次、输入框 `demo` |
| 点输入框 → 打字 → 立刻点确定 | 点一下 / 输入文字「order-42」 / 点一下（**无多余等待**） | 4.9s，3 步全 ok | ✓ 按钮 1 次、输入框 `order-42` |
| 打字 → 点确定 → 停顿 → 再点确定 | 点一下 / 输入文字「x1」 / 点一下 / 等一下 2.01 秒 / 点一下 | 8.4s，5 步全 ok | ✓ 按钮 **2 次**、输入框 `x1` |

**闭环 3/3 = 100%**。三个场景刻意覆盖三种结构（带停顿 / 不带停顿 / 两次点击），
所以能说明"这套推断+回放不是只在一种情况下对"；点击落点与真值逐像素一致
（按钮 `(319,310)`）。样本仍偏小（3 场景 × 1 遍），要出统计口径得做多轮跑批。

## 三、这一波真机暴露并修掉的问题（都不是测试瑕疵）

1. **钩子回调里抓屏会丢用户的输入**（WP1）。Windows 底层钩子有超时限制，回调慢过阈值
   事件就被丢掉——实测第二次点击没进应用窗口（Tk 命中测试与 Win32 落点窗口都指对了地方）。
   现在回调只记事件，抓帧走后台线程。
2. **页面图必须取自"点击那一刻"的帧**（WP1）。停止后再抓，登录表单早翻页了，
   反查出来的会是完全无关的部件。
3. **SendInput 的结构体大小在 x64 上错了**（WP5，最严重的一个）。
   `INPUT` 是键盘/鼠标/硬件三选一的联合体，大小由 MOUSEINPUT 决定（40 字节），
   手写时只按 KEYBDINPUT 算成 32 → `SendInput` **静默返回 0** →
   `LiveDriver.type_text` 一直回退到 pynput 按键序列，而那条路会被中文输入法拦坏。
   也就是说：**真机上的"输入文字"从来没走通过正确路径**。
   修好后录制阶段与回放阶段的输入都正常。已加结构体大小的回归测试（只测纯函数发现不了）。
4. **改名恢复：自由回答不行，选项式提问才行**（WP4）。让模型自由回答"它现在叫什么"，
   它两次都答「目标不存在」；把本地 OCR 到的词当候选让它挑，一次就对了。
   与 D3 一致：给定标签集的分类很准，自由生成不可靠。
5. **`PageLostCalibTest` 的前置断言过期**（既有失败，与本次改动无关，已用 git stash 验证）：
   "暖色改版屏上整窗模板应失配"在 M2 加上 ORB 特征兜底后已不成立——特征匹配能在改版页上
   正确定位（左上偏差 3px，是真命中）。换成新 fixture 后这条恢复路径才重新被测到。

另记一次**我自己的事故**（已写进 WP3 的提交信息）：用 edit 删一个"多余空行"时，把
`def _exec_condition` 那一行并进了上面的注释，整个方法消失，而语法检查照样通过——
是 L3 模板测试抓出来的。教训：编辑后必须跑相关测试，不能只做语法检查。

**样本量的诚实说明**：三个场景各跑一遍，覆盖三种操作结构。它能说明"闭环在多种结构下
都成立"，但**不是统计意义上的成功率**。要给出可靠的 ≥90% 口径，需要像 M2 那样做跑批
（多场景 × 多轮）。建议放到 M4 与"录制回放跑批"一起做，本次不虚报。

**D3 的两次运行差异**（同一套用例、同一个模型）：92% 与 100%。模型有波动，所以
文档里两个数都留着、引用取保守值，延迟也按区间看。两次合计 24 例判对 23 例（96%），
唯一失手那次模型答的是「不确定」——保守而非瞎猜，但**仍如实算作判错**。

## 五、三条口径决定（用户 2026-09-11 定，全部落地）

1. **「放弃/删除录制」不算人工介入** ✓
   —— 与现有代码口径一致：`bench.py` 的 `MANUAL_KINDS` 只把 `not_found` / `outcome_fail`
   这类**异常求助**算人工介入，用户主动放弃录制从来不在其中（它没打断自动流程，
   只是没生成脚本）。
2. **云端调用次数与延迟/成本计入验收指标** ✓
   —— 为此新增了 `engine/ai.py::CloudMeter`（次数 / token / 延迟 / 失败），
   在 `ZhipuVLM._chat` 的真实调用点计量（**失败的调用也计入**，它同样花时间、可能已计费）；
   `ai.stats` IPC 方法可随时查询；每次 `script.run` 会先归零、跑完把用量写进运行报告
   与 `event.run_done`（界面因此能显示"本次运行调用了云端 N 次"）。
   实测数字见上表与 `docs/M3_D3验收数据.md` 的「云端用量」一节。
   **不写币值**：单价随牌价变动，只报 token 数，换算是使用方的事。
3. **D3 答「不确定」按判错计** ✓
   —— 不给"保守加分"。理由是验收要回答的是"它到底能不能判出来"，判不出来就是没做到；
   算成对会让准确率虚高、掩盖真实能力。
   已落成**可执行**的口径：评测脚本里抽了 `is_correct(truth, got)` 纯函数（**精确相等**），
   并由 `engine/tests/test_d3_eval.py` 钉住三条边界——精确命中才算对、
   「不确定」算错、「没出现」也不算对（两者都表示说不清）。
   两次运行里各因此扣掉一例（那次模型答的正是「不确定」）。

顺带把用例集的前提也变成了可检验的：每个用例补了「屏幕上写着的字」，于是测试能断言
**标成直白的用例、本地关键词表必须判得对；标成含蓄的、必须判不出来**——
前提错了的话，云端那一路的准确率就没意义（拿现成关键词能判的题去考语义等于白考）。

## 六、一个未定位的脚手架问题（如实记下，别当成已解决）

同一个进程里连续跑**第二个场景的回放**时，主线程会 forever 卡在 `tkinter.update()` 里
（faulthandler 的全线程栈显示只剩主线程，回放线程早已结束）。已经排除的原因：

- **不是引擎的录制路径**：第二个场景的"录制中 → 反查完成"都正常打印出来了；
- **不是回放本身**：同一个场景单独跑（独立进程）100% 通过；
- **不是死锁**：`ocr_engine()` 不持 `_OCR_LOCK`，OCR 的挂死保护也没被触发。

嫌疑在"Tk 事件循环 + 合成输入在同一进程里反复折腾"（Windows 模态循环的典型症状：
栈停在 `update()` 里出不来）。**规避办法**：一个场景一个独立进程，这也是现在脚本的
默认行为（`e2e_replay.py` 不带参数就逐场景起子进程）。定位留到 M4 —— 它只影响这个
测试脚手架，不影响引擎本身。

过程中脚手架自己踩的两个坑也记一下（都属于"静默失败"）：
`_write_result` 原来是 `except Exception: pass`，把 `import json` 漏掉的 NameError
静静吞了，于是父进程看到的是"子进程退出码 0 但没留下结果"，白查一轮；
子进程写结果文件时用了**循环内序号**（每个子进程都是 1），三个场景互相覆盖成同一个文件名。
两处都改成"出错喊出来 + 用全局序号"。

## 七、已知限制（不假装支持）

- **中文输入法组合出来的字录不到**：钩子只看得到原始按键，录到的是拼音字母。
  回放侧不受影响（Unicode 直发，见上），缺的是录制侧。要彻底解决得接 IME 层。
- **滚轮与单独功能键**只留痕（`unsupported`），不生成动作——`schema.ACTIONS` 里没有对应项，
  硬塞会做出一个假步骤。UI 会如实告诉用户"这一步没录进去"。
- **D3 与自校准的用例集都是合成屏幕**：可复现、可回归，但覆盖面有限，数字是能力证明，
  不是上线成功率承诺。
- **自校准端到端约 9–13 秒**（本地多区域 OCR 7.5s + 一次云端往返 2–4s）。
  当前实现已是"hint 圈优先、整图行带兜底"，再快就要牺牲召回。

## 九、收口后按**用户试用反馈**做的修正（2026-09-11）

用户上手试后提了两条，都是真问题（尤其第二条：我原来只做了停止热键，
没意识到"用户在自己界面里的操作会被录进去"）：

1. **开始录制时窗口立刻最小化** —— 应用窗口很大，开着会挡住用户要操作的东西。
   现在点「录制我的操作」后窗口自动最小化，并弹一条**系统通知**告知停止热键
   （窗口一最小化，界面里那行提示就看不见了，通知是唯一能送达的地方）；
   停止/放弃/按热键结束后窗口自动恢复——用户多半是人在别的程序里按热键停的，
   不该还要去任务栏把窗口找回来。顺手关掉了 Electron 的后台节流
   （`backgroundThrottling: false`）：窗口最小化时界面逻辑不能被节流，
   否则"按热键停止"之后界面可能过很久才收尾。

2. **用户在「脚本构建器」里的操作不计入步骤** —— 钩子是全局的，用户为了点「停止」
   切回来、点一下按钮，那一串会被如实录成积木：录出来的是"操作脚本构建器"，
   不是他真正想自动化的那件事。现在按**窗口句柄**过滤：点击/滚轮看落点窗口、
   按键看前台窗口，命中自家窗口就丢弃；录制结束会如实告诉用户"你在本应用里的
   N 次操作没有计入步骤"。

   一个刻意的取舍：**任务栏点击仍然会被记录**——"点任务栏图标切到某个程序"
   常常是自动化流程合法的第一步，不能一刀切掉；而"停止录制"现在已经不需要
   碰任务栏了（热键 + 自动恢复窗口）。

验证（`smoke/diag/verify_self_filter.py`，真机）：点脚本构建器标题栏 → 被丢弃；
点桌面空白 → 正常记录且坐标一致；反向对照（不带过滤）→ 应用内的点击**会**被录下来，
证明确实是过滤起的作用。界面自测 34 → **36 条全过**（新增"开始录制后自动最小化"
与"放弃后自动恢复"两条）。引擎侧新增 7 条过滤单测。
