# M3 自校准 AI 化（WP4）· 验收数据

生成时间：2026-09-11　模型：`glm-4.6v`　脚本：`smoke/diag/calib_ai_eval.py`

## 测的是什么

界面小改版把菜单**改了名**（`库存查询` → `存货台账`），脚本里记的旧目标在新界面上找不到。
整条自校准链要跑通：

```
本地三级定位失败 → 云端语义确认 → 云端答出「它现在叫什么」
→ 本地在圈区内精确定位 → 重采集部件模板并写回 → 写回前自检
```

前置（脚本会打印）：页面模板在改版屏上仍命中 ✓、旧目标在新屏上确实不可见 ✓
—— 场景成立，否则这次评测证明不了什么。

## 结果

| 配置 | 结果 | 说明 |
| --- | --- | --- |
| 对照组：不接 AI | **恢复失败**，旧值原样保留 | 按设计走「低置信 → 人工确认」，不瞎改脚本 |
| 云端 AI（选项式提问） | **恢复成功** ✓ | 文字恢复为「存货台账」，写回框与真值偏差 **7px** |

## 关键发现：自由回答不行，选项式提问才行（这一轮最有价值的一条）

第一版实现是让模型自由回答"图1那个按钮现在叫什么"。**实测失败**：
模型两次都答「目标不存在」—— 它认不出"存货台账"就是"库存查询"改的名。

改成**选择题**：本地先 OCR 出界面上有哪些词（`工作台 / 订单管理 / 存货台账 / 我的审批`），
把它们作为候选交给模型，只让它挑一个。**一次就对了**（答「存货台账」）。

这与 M3-WP3 的结论一致：glm-4.6v 在**给定标签集**上的分类很准（D3 实测 92%），
在**自由生成**上不可靠。所以凡是能让它做题的地方，就别让它作文。

第二条同类的发现（由一次写错的测试教出来的）：**前缀兼容的改名根本不需要 AI**。
`库存查询 → 库存中心` 共享前缀「库存」，本地"短前缀"启发式直接就命中了。
所以 AI 第二问只在**前缀也对不上**时才被调用 —— 这条已经用测试钉住
（`test_calibrator_rename.py::PrefixRenameTest`，断言 `rename_calls == 0`）。

## 架构边界（本层不越线，有数据佐证）

值得单独说的是：**这一次云端连坐标都没给**。第一问（找目标）返回的是「目标不存在」，
所以自校准没用上任何云端坐标；最终写回的部件框由本地 OCR 给出
（`method=ocr_text`，偏差 7px），云端只贡献了一个**词**。

这正是既定边界想要的样子：**坐标一律来自本地三级定位，云端只做语义**。
即便将来云端粗圈可用，它的角色也只是"把本地搜索范围缩小到 ±100px"，最终坐标仍由本地给出。

## 已知局限（如实记录）

- 用例是**合成屏幕**（同一套 fixture，可复现可回归）；真实产品的改版幅度、字体渲染、
  多语言界面都比这复杂，本表的数字是能力证明，不是成功率承诺。
- 端到端一次自校准约 **9–13 秒**，其中大部分是本地 OCR 多区域扫描（7.5s）+ 一次云端往返。
  如果用户觉得慢，可先只扫 hint 圈（现在的实现已经是"圈区优先"，整图行带是兜底）。
- 恢复失败的路径没有云端参与时是静默的：脚本保留旧值、交给人确认 —— 这是有意的，
  宁可什么都不改，也不能改错。
